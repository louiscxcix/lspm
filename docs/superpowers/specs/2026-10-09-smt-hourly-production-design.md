# SMT 날짜별 시간 생산량 / 목표 / 사유 — 검토용 설계

상태: 사용자 검토 전 시안. 앱·DB·프로젝트 생성·배포는 수행하지 않음.

## 1. 범위와 선택

LS 내부 SMT 라인은 유지하고 독립 SMT 프로젝트를 추가한다. 공유 온톨로지의 기존 라인, 설비, Part, 사람 ID를 프로젝트 membership으로 연결한다. Starpro SMT와 내부 SMT는 동일 설비나 조직으로 자동 병합하지 않는다.

추천: 기존 process map에 날짜/시간 기반 실적 레이어를 추가하고 하단에 시간별 표를 둔다. 별도 대시보드만 만드는 방식은 공정 관계를 보기 어렵고, 모든 사유를 칩 안에 넣는 방식은 지도 밀도를 높이므로 선택하지 않는다.

프로젝트 기능 설정을 저장한다: LS와 MOBIS + HELLA는 WIP Progress 활성화, SMT는 시간별 생산 실적 활성화. 둘은 별도 기능이며 다른 프로젝트에도 설정으로 활성화 가능하다. 비활성화는 데이터 삭제나 권한 부여가 아니다. 현재 비로그인 공개 범위는 LS Production만 유지한다.

## 2. 데이터의 의미

- 생산일과 시간 구간은 America/Mexico_City 기준. 업로드 시각은 별도 기록하며 생산 시각을 덮어쓰지 않는다.
- actualQuantity는 지정 구간에 생산한 수량이다. WIP 잔량도 누적 카운터도 아니다.
- 입력 기준: projectId, lineId, partId/modelCode, stepId, 선택적 machineId, intervalStart, intervalEnd, unit.
- 목표: targetQuantity, planVersion, recordedAt, sourceId. 목표 변경은 새 버전으로 기록한다.
- 실적: actualQuantity, recordedAt, sourceId, revision 및 정정 대상 기록 ID.
- 사유: category, 설명, 대응, verification(reported/confirmed), 관련 실적 ID, 선택적 History Event ID. 여러 사유를 연결할 수 있지만 각 사유의 손실 수량은 근거 없이 배분하지 않는다.
- 사유 분류: material, equipment, quality, staffing, setup, other, unknown.
- 원문에는 텍스트/파일, 시트·행·열, 입력자, 업로드 시각, content hash를 보존한다.
- Part나 설비를 이름만으로 자동 생성하지 않는다. 모델 코드·공정 별칭은 기존 ID와 매핑하며 모호한 행은 미저장 상태로 보여준다.

## 3. 계산과 제한

- 달성률 = actualQuantity / targetQuantity × 100 (목표 > 0일 때만).
- 부족 = max(targetQuantity - actualQuantity, 0); 초과 생산도 별도 양수로 표시한다.
- 미입력은 null. 실제 0 입력과 구별한다. 목표 미입력 또는 0이면 달성률을 표시하지 않는다.
- 목표·실적은 같은 시간 구간/모델/공정/단위로만 비교한다. 구간 길이가 다르면 자동 비례 배분하지 않는다.
- 한 시간보다 짧은 관측은 그 구간 실적으로 표시하며, 실제 관측 없이 시간당 실적을 추정하지 않는다.
- 날짜 합계는 한 생산 측정 기준 공정의 겹치지 않는 구간만 합산한다. 서로 다른 공정의 수량을 더해 일일 생산량으로 만들지 않는다. 기준 공정 미설정이면 일일 전체 생산량 대신 선택 공정 합계를 표시한다.
- pcs와 sheets 등 단위가 다르면 분리한다. 불량/양품 구분 자료가 없으면 '양품 수량'으로 표시하지 않는다.
- 관측 생산량이나 달성률로 미달 원인, WIP, 병목 또는 실제 물류 이동을 확정하지 않는다.

## 4. UI

프로젝트 Production map 상단: 날짜, 시간 구간, Part/모델, 실적 레이어 ON/OFF, 입력 버튼. 기본은 선택 날짜의 마지막 입력 구간. '하루 전체'를 선택하면 각 칩에 선택 공정의 당일 합계를 표시한다.

기존 공정 칩을 그대로 사용한다. 레이어 ON이면 공정명 아래 '실적 220 / 목표 300 pcs', '73.3% · 부족 80', 비교 막대, 사유 요약 한 줄을 표시한다. 목표 미달은 amber 숫자와 '미달' 문구, 달성은 일반 blue, 미입력은 gray와 문구로 구별한다. 색만으로 상태를 설명하지 않는다.

칩 선택 및 관계 하이라이트, ? 상세, zoom/fullscreen 동작은 유지한다. 선택 칩 상세에는 시간별 목표/실적, 복수 사유, 대응, 근거와 기록 이력을 표시한다. 사유는 별도 process node로 만들지 않는다.

하단 시간별 표: 시간 구간, 모델, 공정, 목표, 실적, 달성률, 사유. 행을 클릭하면 해당 시간과 공정을 지도에서 선택한다. 날짜를 바꾸면 기존 지도 구조는 유지하고 숫자 레이어만 갱신한다. 레이어 OFF 시 기존 지도와 선택 상태를 복구한다.

시안의 공정 A/B/C 및 모든 수량·사유는 가상 예시다. 실제 SMT 경로는 미확정이며 시안만으로 DB에 추가하지 않는다.

## 5. 입력

텍스트/Excel 열: 날짜, 시작, 종료, 모델 코드, 공정, 선택적 설비, 목표, 실적, 단위, 미달 사유, 대응.

예: 2026-10-09 / 10:00 / 11:00 / SAMPLE-A / 공정 C / [설비 미입력] / 300 / 220 / pcs / 자재 공급 지연 / 입고 확인 요청.

계획만 먼저 넣거나 실적만 넣을 수 있다. 같은 파일 반복 입력은 무시한다. 같은 측정 키에 값이 다른 입력은 정정 확인을 거쳐 새 revision으로 보존한다. 음수, 비정수, 종료≤시작, 중복·겹친 구간, 모호한 모델/공정 및 단위 불일치는 저장 전에 표시한다. 오류 행을 조용히 버리지 않는다.

## 6. 저장과 구현 순서

1. 프로젝트별 기능 설정 검증/저장 및 독립 SMT 프로젝트 membership. 기존 project_view_settings와 프로젝트 생성/공유 DB 흐름을 재사용한다.
2. WIP 테이블과 별도 시간 생산 계획·실적·사유 테이블, 원문 연결과 정정 이력. 기존 revision/transaction 경계 재사용. History에는 의미 있는 문제/대응만 명시적으로 연결하며 수량 입력만으로 Event를 무한 생성하지 않는다.
3. 입력 파서/명확한 매핑/중복 및 정정 처리, 조회·저장 API. 별도 계산 모듈은 목표 0/null, 미입력/0, 단위와 측정 공정 경계를 검증한다.
4. 기존 지도 칩 숫자 레이어·상세·시간별 표. 생산 수량이 process edge 유량이라는 식의 애니메이션은 넣지 않는다.
5. 로컬 SQLite 외에도 배포 환경의 owner-only Firestore 저장/조회 구현. 현재 cloud-api는 WIP Progress 업로드만 저장하므로 새 측정 자료와 기능 설정 저장 경로/규칙/재로드도 함께 추가해야 한다. 로컬 DB 변경이나 Hosting 재배포만으로 클라우드 저장 완료로 간주하지 않는다.
6. 기능 설정 재접속 유지, 데이터 reload, 동일 업로드/정정, 시간·단위·Part 경계, guest 쓰기 거부, 레이어 복구, 칩 겹침과 모바일/fullscreen을 검증한다. 승인 후 별도 구현 계획과 테스트를 작성한다.

## 승인 기준

독립 SMT 프로젝트에서 날짜/시간별 목표·생산량·사유가 저장되고 재접속 후 조회된다. 기존 공정 지도에서 비교 수치가 읽히며 상세 사유를 확인할 수 있다. LS/MOBIS의 WIP Progress, LS 내부 SMT 연결 및 현재 권한 설정은 바뀌지 않는다.
