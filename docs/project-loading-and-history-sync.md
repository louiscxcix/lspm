# Project loading, viewer passwords and scheduled History

Project list uses the small public catalog, including owner sessions. Private graph, History and upload records load only when opening a project or Global Library. Catalog requests share an in-flight promise and a 30-second cache. A changed private seed version invalidates the previous workspace even when cloud upload revision is unchanged.

Existing owner Firebase password remains unchanged. Project viewers use independent Firebase accounts and read-only projectViews; they cannot read privatePM, raw chat, History, or write observations. Four-character project PINs are supported through a project-specific credential prefix solely to satisfy Firebase's minimum credential length. This adds no security strength: `0000` is unsuitable for sensitive data. Existing passwords of six or more characters remain compatible. Manage password rotations in this chat or the existing owner-only project access settings; passwords are never stored in catalog documents.

The existing PM heartbeat remains at Mexico City 09:00, 12:00, 15:00, 18:00 and 21:00. After verified local History commits, run `node publish-private.js --confirm-private-cloud`. Publishing is idempotent by content hash, writes version chunks first and changes the seed pointer last with a compare-and-swap guard. It preserves cloud-created projects and immutable cloud observation uploads. It does not change owner credentials, viewer passwords or project grants. Publication failure must be retried independently of chat ingestion checkpoints. Never place chat content in public-workspace.json or projectViews. History updates are data publication, so Hosting need not redeploy every three hours; refresh the owner page to load the new version.

This is a desktop heartbeat, not an always-on server. Codex, Kakao and the Mac must be available. No GitHub push, new machine/role assignment, inventory change or automatic code release is part of this schedule.
