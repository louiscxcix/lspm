# Production Progress — 모델 코드별 WIP + Celonis식 재생 통합 계획

상태: 설계안. 구현, DB 변경, 실제 수량 입력, 배포 전.

## 1. 확정 요구사항

- Excel 공정별 숫자는 WIP, 생산량이나 누적 통과 실적이 아니다.
- 수리 재공 현황, 합계 행은 제외한다. EA/Box는 공정 수량이 아니다.
- 모델 코드별 품목을 구분한다. 같은 이름의 LH/RH/Upper/Lower라도 코드가 다르면 합치지 않는다.
- 일반 Process map은 확인된 공통 공정 경로를 공유할 수 있다.
- Production Progress에서는 선택한 코드별 품목의 경로와 수량을 따로 표시한다.
- Progress ON: 선택 품목의 정상 공정만. 사람·설비·Component·NG 경로는 제외한다.
- Progress OFF: 기존 Process map, 선택, 줌, 위치를 복원한다.
- 업로드/저장 시각을 관측·기록 시각으로 사용한다. 멕시코 시간으로 표시한다.
- 기존 History, 공정, 설비, 담당자 연결은 자동 변경하지 않는다.

## 2. 온톨로지 — 제품, 코드별 품목, 경로, 관측 분리

### 2.1 제품 구조

기존 Part와 part_of를 재사용한다. 새 대형 객체 체계는 만들지 않는다.

```text
G65 (Family)
  └─ Main / Jewelry / Upper / Lower 등 기존 제품 분류
      └─ LH / RH 등 기존 variant
          └─ 모델 코드로 식별하는 제조 품목 (Part)
```

모든 품목에 모든 계층을 강제로 만들지는 않는다. 확인된 분류만 연결한다.
모델 코드 품목에 name, modelCode, codeNamespace, sourcePartName, productionFamily,
productFamily, side, position, mappingState, sourceEvidence를 보존한다.
codeNamespace는 예를 들어 LS MES이며 프로젝트 ID가 아니다. 전역 DB에서 동일 품목을
재사용하고 프로젝트는 membership으로 해당 품목을 참조한다.

식별 키는 codeNamespace + modelCode. 앞뒤 공백을 정리하되 코드의 문자·숫자·선행 0을
보존한다. 서로 다른 코드의 같은 이름은 다른 품목. LH/RH나 SL 표기만으로 코드 및
경로를 추측하지 않는다. 이름·설명 별칭은 원문과 별도 보존한다.

이미 정확한 코드가 있는 기존 Part는 재사용한다. 코드가 없는 기존 Part와 신규 코드의
동일성이 확인되면 기존 Part에 코드를 부여할 수 있다. 여러 코드가 대응하면 하위 품목을
만들며 기존 상위 객체와 과거 관측은 유지한다. 모호한 과거 기록은 재배정하지 않는다.

### 2.2 공정 경로 공유

기존 Production Step, precedes, applies_to 관계를 사용한다. 확인된 동일 경로라면
공정 객체를 코드마다 복제하지 않고 같은 Step을 여러 품목에 연결한다.

- 일반 맵: 동일 Step ID를 한 번 그리며 관련 코드별 품목을 상세에서 확인한다.
- Progress: 같은 Step도 화면에서는 품목 ID + Step ID의 개별 chip으로 그린다.
- 화면 복제는 DB 공정 복제가 아니다. 상세·History는 원래 Step ID를 참조한다.
- 공정 이름만 같다고 경로를 합치지 않는다. 순서, 실제 공정/설비 조건이 확인되어야 한다.
- Parent/Family 수준 조회가 하위 코드 수량을 중복 합산하지 않도록 집계 대상은 코드 품목만 지정한다.

### 2.3 WIP 관측

한 업로드는 한 Snapshot. 그 아래 각 비어 있지 않은 셀은 Observation이다.

```text
Snapshot: ID, project, 업로드 시각, source, 저장 상태
Observation: snapshotId, codedPartId, 원문 모델 코드/품목명,
             stepId, 원문 공정명, quantity, unit, 원문 행/열
History Event: 해당 Snapshot의 업로드 사실, 대상 품목·공정, source 근거
```

원문을 보존하고 관측만 추가한다. 관측 저장과 현재 공정 구조/재고 상태 변경은 별개다.
동일 원문 재전송은 중복 확인하며 의도적인 새로운 관측은 새로운 Snapshot으로 기록한다.
같은 시간·품목·공정의 수정은 명시적인 정정으로 다루고 기존 근거를 삭제하지 않는다.

## 3. Excel 붙여넣기

### 3.1 사용 흐름

Excel 헤더와 품목 행 복사 → Paste Excel → 유효하면 바로 저장 → History + WIP 저장
→ 선택한 코드별 Progress에 반영. 매번 Part를 미리 선택할 필요는 없다.

TSV를 우선 지원하며 기존 단순 텍스트/CSV 입력은 유지한다. XLSX 파일 입력은 기존
Excel 파서를 재사용하여 동일한 매핑/검증을 통과하도록 한다. 클라우드에서 XLSX 지원을
원할 경우 브라우저 파서 또는 백엔드 범위를 별도 확인하며, 복사 입력을 먼저 완성한다.

### 3.2 표 해석

- 차종·고객사: 보조 식별정보.
- 모델명: 모델 코드. PJT명: 원문 품목명.
- 다중 헤더를 읽어 수리 재공 현황의 열을 제외한다.
- 공정 헤더와 각 숫자의 원문 열 위치를 보존한다.
- 합계·소계·품목명 없는 요약 행은 Observation을 만들지 않는다.
- EA/Box, 기타 포장 환산 열은 공정으로 처리하지 않는다. 자동 환산도 하지 않는다.
- 빈칸/대시는 미기록, 0은 실제 0개. 새 Snapshot의 빈칸이 과거 수량을 0으로 바꾸지 않는다.
- 숫자의 천 단위 쉼표는 허용, 음수·소수·수식 오류·문자 수량은 거절한다.
- 숨겨진 Excel 열이 복사 범위에 포함될 수 있으므로 화면 위치나 색상에 의존하지 않는다.
- 수리 영역의 상위 헤더가 빠졌으면 열 제외를 임의로 추측하지 않는다. 헤더 포함 복사나 제외 열 확인을 요청한다.

### 3.3 코드와 공정 매핑

코드 우선, 이름은 보조정보. 새 코드가 기존 품목과 확실히 연결될 경우 매핑을 저장하고
다음 업로드에서 재사용한다. 사진에서 불명확한 코드를 임의 등록하지 않는다.

공정 별칭 예: FW Download(LS) → 해당 품목의 FW download. EOL Ass'y와 EOL PCB,
Vision과 Visual은 서로 다른 공정으로 보존한다. 표에 있는데 경로가 없는 공정은 자동
생성하거나 다른 공정으로 대체하지 않는다. 숫자를 원문 후보에 보존하고 매핑을 요청한다.

유효 데이터는 바로 저장 가능. 알 수 없는 코드·공정·동일 셀 충돌이 있으면 저장 전
해당 문제만 표시한다. 조용히 일부를 버리고 성공으로 처리하지 않는다.

## 4. UI — 큰 맵 + 코드별 선택 + 하단 재생바

기존 Celonis식 색상·pill·hexagon·줌·전체화면을 유지한다. 별도 분석 대시보드나
오른쪽 상시 패널을 추가하지 않는다. 화면 대부분은 맵이다.

### 4.1 상단

- 기존 Production line 선택 유지: SMT / LDM / Nexlide / TEM.
- 품목 선택은 Family → 제품 → LH/RH 등 → 코드 품목 체크박스.
- 코드·품목명 검색, 복수 선택, 선택 해제, 선택 칩 제공.
- Progress 모드에서 미선택 품목은 제외하고 선택한 코드만 개별 경로로 표시한다.
- 표시: WIP / WIP + 변화. 비교 기준: 이전 관측 / 선택 기간 시작 관측.
- Paste Excel, 줌, Fit, 전체화면 유지. 선택·시점·재생 속도는 보기 설정으로 기억한다.

### 4.2 맵 배치와 chip

코드별 정상 경로를 각각 한 줄로 배치한다. 같은 확인된 경로의 품목끼리 인접하게
배치하며 데이터 변화 때 좌표를 다시 계산하지 않는다. NG/사람을 정상 경로 중간에 넣지 않는다.

chip 기본 정보: 공정 이름, 현재 WIP, 변화량. 작은 추세는 선택/주의 chip에만 표시한다.
코드·LH/RH는 경로 라벨에 표시해서 모든 chip에 반복하지 않는다. 동일 공정 이름이어도
코드별 숫자는 섞이지 않는다. 5–6개 품목에서 전체 경로를 보며 줌아웃 시 추세·부가 문구를
줄이고 공정 이름·WIP는 유지한다. 더 많으면 pan/zoom하며 겹침 없이 표시한다.

코드별 다른 단계 길이는 빈 자리로 정렬할 수 있지만 연결이 없는 공정을 새로 만들지 않는다.
좁은 화면은 가로 pan을 사용하며 Part 선택과 재생 컨트롤은 접근 가능하게 유지한다.

### 4.3 하단 시간 재생

10개 관측 시안을 기준으로 기간 선택 손잡이 2개와 재생 커서를 구분한다.
실제 관측 시각별 점, 현재 시각·관측 번호, 이전/다음, 재생/정지, 1×/2×/5×를 둔다.

- 기본 재생은 관측 간격을 압축하는 관측 순서 모드다. 압축 재생이라고 표시한다.
- 새 관측 시각에 도달할 때 숫자가 바뀐다. 중간 수량은 선형 보간하지 않는다.
- 해당 시점에 새 값이 없으면 마지막 관측을 유지하며 마지막 확인 시각을 표시한다.
- 관측 전 구간은 미관측. 일부 품목만 업데이트되면 다른 품목은 오래된 관측임을 표시한다.
- 선택 기간 시작 시점의 비교값도 실제 마지막 관측을 사용하고 없으면 비교 없음으로 표시한다.
- 저장 시간 기준으로 여러 번 즉시 올린 데이터는 짧은 간격으로 나타난다. 이를 몇 시간 생산으로 바꾸지 않는다.

### 4.4 애니메이션과 주의 표시

- 변경된 chip만 짧게 강조하고 증가/감소 기호를 표시한다.
- 증가가 무조건 나쁜 것은 아니므로 기본 delta 색상은 중립, 주의 후보만 amber.
- 실제 제품이 이동하는 점이나 수량 비례 흐름선은 사용하지 않는다. 화살표는 경로만 뜻한다.
- Reduce motion에서는 강조 애니메이션 없이 값만 갱신한다.
- 3회 연속 증가, 사용자가 설정한 WIP 상한 초과, 오래된 관측을 주의 후보로 표시한다.
- 값 유지 또는 증가만으로 정지/병목/불량을 확정하지 않는다.
- 클릭하면 기존 상세 방식으로 관측 시각·10개 관측 추세·비교값·원문·연결 History를 본다.

## 5. 분석 범위

계산 가능: 특정 시각 마지막 WIP, 이전/기준 관측 대비 증감, 관측 최솟값/최댓값,
실제 관측 간 증가 추세, 관측 나이. 품목 코드·단위별로 계산한다.

계산하지 않음: 실제 생산량, 처리량, 특정 제품 이동, 사이클타임, 개별 대기시간.
WIP 차이는 투입·반출·수리·이동이 섞인 순변화다. 이동 로그 없이는 그 원인을 알 수 없다.
AI 기간 보고서는 이번 범위에서 제외한다.

## 6. 기술 적용

- ontology-model/project-store: 기존 Part 필드 허용·검증·입력/출력에 모델 코드 정보 반영.
- workflow: 코드 품목에 공유 applies_to 연결; 일반 network는 기존 Step ID로 중복 제거.
- progress.js: TSV 헤더 감지, 코드 매칭, 공정 별칭, 모델별 관측 검증/분석.
- progress-view.js: 모델별 렌더 키, selector, 고정 좌표, 시간 컨트롤, 변경 강조.
- local-store/history-store: source/product_code를 관측에 보존하고 revision/transaction 유지.
- cloud-domain/cloud-api: 동일 검증·식별·관측 근거를 보존. 로그인/권한 규칙 유지.
- public build: 모델 코드별 기본 맵 구조만 기존 공개 범위대로 반영하며 비공개 원문은 공개하지 않는다.

현재 로컬 SQLite와 개인용 Firestore의 Progress 저장은 분리되어 있다. 구현 시 먼저 로컬
검증한 다음 개인용 seed/클라우드 관측 호환성을 확인한다. 기존 cloud records를 덮어쓰거나
로컬 기록과 자동 양방향 동기화하지 않는다. 실데이터 수정 전 백업과 매핑 변경 이력을 남긴다.

## 7. 구현 순서와 완료 기준

1. 실제 Excel 복사 표 확보 → 모델 코드/품목 매핑 → 미확정 코드 목록 확인.
2. Part 코드 구조와 공유 경로 적용 → 기존 History/공정/선택 기능 회귀 검증.
3. 직접 붙여넣기와 자동 제외 구현 → 코드별 WIP + History 원자 저장.
4. 코드별 Progress 경로, 선택, 비교, 재생, 변화 강조 구현.
5. 10시점의 명시적 가상 관측으로 5–6품목 시험. 실 DB에 샘플을 섞지 않는다.
6. 로컬/개인용 클라우드 호환 및 공개/비공개 분리 검증 후 승인된 범위만 배포.

필수 검증: 같은 이름·다른 코드 분리, LH/RH 수량 분리, 공유 Step에서도 Progress 분리,
수리/합계/EA Box 미집계, 빈칸과 0 구분, 알 수 없는 열의 무단 매핑 없음, 과거 기록 유지,
Progress OFF 원복, 10개 관측 재생/seek 일관성, chip 겹침 없음, 공개 원문 누출 없음.

## 8. 시안 읽는 법

시안 모델 코드 MODEL-A/B/C와 숫자는 가상이다. 실제 DB 등록값이 아니다.
시안은 큰 맵, 모델별 경로, WIP 숫자와 delta, 하단 관측 재생 구성을 설명한다.
Celonis Process Explorer의 zoom/metric/playback/seeker 원리를 참고하되 실제 case 이동
애니메이션 대신 WIP 관측의 시간 변화만 표시한다.

참고: https://help.celonis.com/cpm46/en/process-explorer

## 9. 로컬 구현 결과 (2026-10-08)

기존 SVG 칩을 그대로 사용한다. Progress에서만 모델별 가로 공정 경로와 WIP/변화량을
표시하며, 일반 맵의 공유 공정 DB는 복제하지 않는다. 단위별 관측 분리, 이전 관측 또는
기간 시작 비교, 실제 관측 1–10 선택·시간 재생·구간 선택을 지원한다. 중간 수량이나
실제 부품 이동은 생성하지 않는다. 3회 연속 증가 강조는 적체 후보이지 확정 병목이 아니다.

Excel 셀 복사 붙여넣기 또는 TXT/TSV/CSV 업로드를 지원한다. Progress에서 XLSX 파일
직접 파싱은 이번 범위에 포함하지 않는다. 수리 재공·합계·EA/Box 열은 제외하며 0과 빈칸을
구분한다. 미등록 모델 코드는 이름으로 추정하지 않고 저장을 차단한다.

실제 코드는 로컬의 ‘모델 코드 등록’에서 기존 Part 공정과 명시적으로 연결한다.
기존 Part와 과거 관측은 그대로 유지한다. 일반 Part 편집에서도 코드 필드를 관리할 수 있다.
읽을 수 있는 실제 코드 표가 아직 없어 실제 모델 코드를 임의 등록하지 않았다.
6개 모델 × 10개 관측 검증은 임시 DB에서만 수행했다.

SQLite 및 클라우드 저장 모듈의 코드·원본 좌표 보존은 테스트했다. 실제 Firebase 배포나
Firestore 변경은 하지 않았다. 클라우드 화면의 모델 신규 등록은 기존 전체 DB 쓰기 권한
제약 때문에 숨겨 두며, 로컬에서 등록 후 승인된 별도 게시 절차를 사용한다.
